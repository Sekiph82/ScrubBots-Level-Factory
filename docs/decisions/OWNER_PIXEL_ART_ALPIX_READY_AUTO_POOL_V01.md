# OWNER DECISION — Pixel Art Alpix Production + READY Auto Release Pool V01

Date: 2026-10-09
Repository: `Sekiph82/ScrubBots-Level-Factory`
Status: OWNER-LOCKED

## D1 — PIXEL ART provider model

PIXEL ART has one real provider selector. Minimum supported provider choices:

- `ALPIX (Claude)`
- `MAGNIFIC`
- `PIXELLAB`

The provider actually used must equal the visible selection. No fake provider label.

## D2 — Single generation

For Single mode the owner supplies:

- prompt;
- output size;
- provider;
- optional reference/notes/background intent only when already represented by the master UI.

Pressing Generate creates exactly one PNG through the selected real provider path.

Factory Studio does not synthesize or rewrite the user's prompt into a hidden batch plan.

## D3 — ALPIX (Claude), no extra API billing

`ALPIX (Claude)` must use the locally authenticated Claude Code subscription session and the installed Claude Alpix plugin/MCP/tooling.

It must not use an Anthropic API key, paid Anthropic API fallback, hidden metered API route, or browser automation.

The implementation must discover the actually installed Alpix tool/plugin identity from the local Claude configuration. Do not guess tool names.

If Alpix/Claude subscription capability is unavailable, fail closed with a short status and preserve work.

## D4 — CSV batch for ALPIX

When provider = `ALPIX (Claude)` and the owner chooses a CSV:

- Factory Studio reads the requests already present in the CSV;
- it processes rows one by one, in CSV order;
- it sends each row's request to Claude + Alpix;
- it saves each successful PNG before advancing;
- it persists job state after every row/state transition;
- completed rows are never repeated merely because the app restarts or a limit is hit.

Factory Studio does not generate the CSV, invent the batch list, or pre-compose a new set of prompts.

## D5 — Usage-limit pause/resume

The legacy EXE behavior is authoritative for resumability.

If Claude usage limit is reached:

- current job transitions to `LIMIT`;
- batch stops cleanly;
- completed rows remain complete;
- the first unfinished row remains resumable;
- no completed PNG is regenerated;
- no row is marked FAILED merely because the subscription limit was reached.

When the limit resets and the owner presses the existing batch primary control in its Resume state, execution continues from the first incomplete row.

The Resume state must occupy the master-defined batch action location. Do not add a new production panel.

## D6 — Legacy EXE reuse

The earlier owner-supplied `ScrubBots Level Factory(3).exe` is a PyInstaller Python 3.12 application containing:

- `pixelart_app.py`;
- `art_producer.py`;
- `find_claude()`;
- `claude_draw(prompt, size, out, notes, fill_bg, ref)`;
- `ArtJob.open_or_create(...)`;
- `ArtProducer.run()`;
- `read_rows(...)`;
- row state progression `PENDING -> DRAWN -> VALIDATED -> IMPORTED`;
- CSV SHA-256 job identity;
- `LIMIT`, pause/resume, stop and per-row redo semantics.

The new Factory Studio must port/reuse this proven job/resume architecture rather than re-inventing it.

The legacy EXE's Claude path used Claude Code subscription login and a pixel-art skill. The new `ALPIX (Claude)` adapter keeps that subscription/job architecture but invokes the actually installed Alpix plugin/MCP for drawing.

## D7 — External PNG intake

LEVEL FACTORY accepts:

- a PNG generated by PIXEL ART;
- one external PNG;
- multiple external PNGs;
- an existing CSV/batch source referencing external PNGs.

All enter the same canonical Level Factory pipeline.

## D8 — Immutable PNG-to-level bundle

For every imported/generated PNG, all derived artifacts stay matched under one immutable identity:

- source PNG identity/hash;
- LevelData JSON;
- supply plan;
- solver proof;
- replay result;
- Difficulty V1 result;
- metadata;
- artworkCellCount / voidCellCount;
- publication identity.

A derived artifact may never silently attach to another PNG.

## D9 — Automatic READY to Release Pool

Owner ACCEPT is no longer required to enter Release Pool.

When canonical pipeline result is truly READY:

- supply is valid;
- official solver is SOLVED;
- replay is WIN;
- Difficulty V1 exists;
- required QA/load checks pass;

then the candidate automatically becomes Release Pool eligible.

The owner approval gate moves to publication: nothing reaches players until the owner explicitly publishes from RELEASE POOL.

## D10 — Accept / Reject buttons under auto-pool

The master visuals remain unchanged.

- `Reject` excludes/quarantines the selected READY candidate from Release Pool.
- `Accept Level` idempotently includes/restores the selected READY candidate in Release Pool.
- A fresh READY candidate defaults to included automatically.
- Neither button publishes content.

This preserves master fidelity while making READY -> Release Pool automatic.

## D11 — Automatic level ordering

Do not invent a parallel level-number allocator.

Reuse canonical campaign/release-order authority.

For batch processing:

- successful READY candidates preserve source order;
- failed/unsolved candidates consume no publish order;
- Release Pool shows deterministic next-order projection/reservation;
- final publication plan resolves contiguous level numbers against current game catalog/history;
- excluding an item before publish must not leave a production level gap;
- retries/resume are idempotent and do not reshuffle already stable successful identities unnecessarily.

## D12 — Publish remains explicit

RELEASE POOL is the human approval surface.

Only owner-triggered Publish/Upload starts publication.

Publication remains:

Release Pool -> ScrubPack -> preflight -> STAGING -> verification -> exact production approval -> R2 Production -> ScrubBots remote content.

No READY event may publish automatically.
