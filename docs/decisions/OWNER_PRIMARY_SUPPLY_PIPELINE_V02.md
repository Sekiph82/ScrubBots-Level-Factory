## 1. Core owner rule

The supplied ZIP is not an add-on to an existing solver/supply/difficulty architecture.

It becomes the Level Factory's canonical production backend for:
- supply planning;
- supply candidate generation;
- screening/ranking;
- real game solve;
- solver replay/WIN verification;
- supply scoring;
- solution verification;
- final game Difficulty V1 measurement;
- supply export.

Do not add extra acceptance gates or alternative solver/difficulty authorities unless the owner explicitly requests them.

The EXE supplied later for inspection is **not** part of this implementation and must not be modified, copied, ported, or used as product authority.

## 2. ZIP behavior that must remain unchanged

Preserve the owner ZIP behavior for:
- `SupplyOptimizer` search structure;
- `ScreeningSimulator` as ranking/screening only;
- real `ScrubBotsSolver` / Godot bridge as acceptance authority;
- `SolvabilitySolver.solve`;
- `SolvabilitySolver.replay`;
- ZIP WIN/replay verification;
- `SolutionVerifier` hard invariants;
- `SupplyScorer` weights;
- default candidate count = `300`;
- one original candidate + up to three mutations;
- screening budget = ZIP default `3000`;
- viability budget = ZIP default `3000`;
- real solver budget = ZIP behavior, i.e. no Factory override unless explicitly supplied; current game canonical defaults remain authority;
- mean-batch-size seed ranges;
- internal automatic image-complexity/search-band heuristic;
- bounded search rounds/mutation behavior;
- no global robot-count cap;
- dynamic supply depth; no fixed 18-row contract.

The owner ZIP's solver+replay WIN gate is sufficient acceptance authority. Do **not** add a mandatory ProductionGameplayHost/runtime WON gate.

## 3. Supply layout owner decision

Shipping supply layouts must support:
- 3 columns;
- 4 columns;
- 5 columns.

Visible preview depth is fixed at:
- 3 rows.

The owner has **not** authorized an automatic column-count chooser.

Therefore:
- expose column count as an explicit level-generation/supply setting with allowed values `3|4|5`;
- preserve ZIP-compatible default `3` until the owner changes that default;
- do not infer column count from difficulty;
- every solver/screening/export/load path must use the selected column count consistently;
- hidden FIFO depth remains dynamic and may exceed 3 rows.

The Scrubbots game already has `BatchSupplyEngine` support for 3..5 columns. Any remaining fixed-three loader/UI/test contract must be adapted narrowly to 3..5 while preview depth remains exactly 3.

## 4. Slot-count owner decision

Level generation/solve/difficulty must use the baseline slot contract only.

The `+1 Slot` booster must not influence:
- supply generation;
- candidate ranking;
- canonical solve used for level acceptance;
- difficulty measurement used for level placement.

Do not generate a level assuming the player will use a booster.

## 5. Requested difficulty is removed from Level Factory

There is no owner-selected requested difficulty in ScrubBots Level Factory.

Remove user-facing/input concepts such as:
- EASY/MEDIUM/HARD/VERY_HARD requested target for artwork generation;
- requested difficulty for supply generation;
- target-difficulty overrides in the Level Factory production flow;
- presets/CLI/UI fields whose purpose is to ask the owner what difficulty to generate.

Artwork is generated/imported first without requested difficulty.

Then the ZIP pipeline generates and solves supply.

Final level difficulty is measured afterward by the current Scrubbots `LevelDifficultyAnalyzerV1`.

Important:
- keep the ZIP's internal automatic image-complexity/search-band heuristic;
- remove the external/user target override only;
- do not replace it with a new owner-facing difficulty control.

## 6. Artwork input owner decision

Level Factory artwork stage must support both:
1. artwork generated by the Level Factory's artwork-generation system;
2. artwork uploaded/imported from outside by the owner.

Do not use the inspected EXE as implementation source merely because it has import UI.

Uploaded artwork must enter the same canonical artwork/palette validation path as generated artwork.

### Background/alpha behavior

If the owner requests a background during artwork generation:
- generate/fill the background during artwork creation so the intended level image is full-canvas.

If the owner does not request a background:
- preserve transparency;
- do not silently invent/fill a background afterward.

Transparent artwork may remain a valid artwork asset. If the current shipping game LevelData cannot publish transparent cells, the system must state that production publish is unavailable for that artifact rather than silently changing the art.

## 7. Difficulty scorer owner decision

Do not change the ZIP `SupplyScorer` weights.

SupplyScorer remains candidate ranking/tuning evidence, not final production difficulty authority.

Final production difficulty comes from the current game `LevelDifficultyAnalyzerV1`.

## 8. Mean-batch seed owner decision

Keep the ZIP's current mean-batch-size seed ranges unchanged for now.

They remain internal tuning seeds, not owner-requested difficulty.

## 9. Publish owner decision

After all canonical ZIP pipeline checks are complete and the owner review disposition is ACCEPT:
- publish automatically to the Scrubbots game pipeline;
- do not require a second manual Publish button.

Publishing must still fail closed on file/path/schema/identity errors.

Owner review remains the human approval boundary.

## 10. Level progression owner decision

Do not assign final progression position before solve/difficulty analysis.

After the level has:
- a solver-proven supply;
- replay/WIN verification;
- official Difficulty V1 / Challenge Score;

determine its progression position from the calculated difficulty.

Do not use requested difficulty because requested difficulty no longer exists.

Preserve stable internal level identity so progression reordering does not require destructive renaming of immutable artifacts/save identities.

The exact insertion/tie-break policy must be deterministic and documented by the implementation.

## 11. Level Factory architecture

Keep the Level Factory functionality that the ZIP does not replace:
- artwork generation;
- external artwork import;
- canonical palette/artwork validation;
- Factory Studio UI/workspace;
- source library;
- owner review;
- revisions;
- session/failure recovery;
- comparison;
- provenance/history;
- final game handoff/publish shell.

Make the ZIP-derived backend the single production path for:
- supply;
- solve;
- difficulty.

Do not retain a second competing production solver/difficulty implementation.

Historical M03/M04 solver/difficulty files may be removed from active product source when no longer required by retained non-production contracts. Git history is the archive.

## 12. Canonical pipeline

```
GENERATE ARTWORK or IMPORT ARTWORK
 -> canonical palette/artwork validation
 -> ZIP PixelAnalyzer
 -> ZIP internal automatic search band
 -> ZIP BatchPlanner
 -> ZIP SupplyCandidateGenerator
 -> ZIP ScreeningSimulator (ranking only)
 -> ZIP SupplyScorer
 -> real Scrubbots SolvabilitySolver.solve
 -> real Scrubbots SolvabilitySolver.replay
 -> ZIP SolutionVerifier
 -> current game LevelDifficultyAnalyzerV1
 -> ZIP SupplyExporter
 -> ZIP/game load check
 -> owner review
 -> automatic publish
 -> deterministic difficulty-based progression placement
```

No mandatory ProductionGameplayHost runtime gate is inserted.
